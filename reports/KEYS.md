# Ключи карт в СКУД Gate — как это устроено

> Обновлено: 2026-11-18 15:00 (Europe/Kaliningrad).
> Относится к приложению `reports/` — мониторинг и отчёты, порт 8110 на LXC `192.168.2.193`.
> Общая документация приложения — `README.md`, состояние проекта — `../STATE.md`.

## Коротко

Пропуск, выданный в приложении, **открывает двери**, а проход в журнале виден
**с именем**. Цепочка целиком:

```
Пропуска → «Выдать пропуск» (карта + двери)
   → приложение пишет SQL-задание в очередь C:\GATE\_skud_queue\
   → приложение кладёт туда же zz_gateserv_restart.cmd
   → агент на сервере Gate (просыпается раз в 2 минуты) выполняет SQL в config.mdb
   → и сразу перезапускает GateServ
   → GateServ при старте читает картотеку и рассылает ключи контроллерам
   → карта открывает двери; проход в журнале — с ФИО
```

Задержка от выдачи пропуска до работающей карты — до 2–3 минут (такт агента
плюс перезапуск службы). Заходить в GateTerm не нужно.

## Три вещи, без которых не работало

### 1. Запись в базу дверь не открывает — нужен перезапуск GateServ

Мы писали карту прямо в `config.mdb` через Jet OLEDB, минуя GateTerm. Служба
`GateServ`, которая общается с контроллерами, об этой записи не узнаёт: она
читает картотеку **при старте**. В базе карта есть, а контроллер её не знает и
отвечает «Нет доступа. Неразрешенный ключ».

Отсюда важное: состояние `gate_state = ok` в приложении означает «SQL
выполнился», а не «дверь знает карту».

Решение: `gate.queue_restart()` после каждого пропуска кладёт в очередь
`zz_gateserv_restart.cmd`. Имя постоянное — несколько пропусков подряд дают
один перезапуск, а не очередь перезапусков.

### 2. Слот ключа — один на устройство, а не на считыватель

Память ключей у контроллера **общая для всех его считывателей**. Значит
`AccessTable.InnerNum` (номер слота) должен:

- совпадать у всех считывателей одного устройства,
- быть свободным на самом устройстве.

Сначала слот выделялся каждому считывателю отдельно, и ключ попадал в занятый
слот. Пример из жизни — устройство «Сан пропускник»:

```
rdr 1 (основной)   слот 1 → сотрудник 1681   ← рабочий ключ
rdr 2 (служебный)  слот 1 → наш новый        ← тот же слот, конфликт
```

Контроллер оставлял чужой ключ, наш не принимал. Проверка на реальных данных:
у 74 из 83 сотрудников, у кого есть оба считывателя одного устройства, слот
одинаковый — то есть Gate выделяет слот на устройство.

### 3. Срок действия в Gate не выставляем

У всех 288 сотрудников `Users.UseExpiry = 0` (срок пуст). Пользователь с
заполненным сроком **не сопоставляется с событием** — проход пишется в журнал
без имени (`UserPtr = 0`, `Name` пусто).

Поэтому `gate.build_add_user_sql()` пишет `UseExpiry = 0`, `ExpiryDate = NULL`,
`ExpiryTime = NULL`, а срок пропуска ведёт наше приложение.

Следствие: ключ в Gate бессрочный, убирать его должно приложение —
см. «Удаление ключа» ниже.

## Что ещё выяснилось про доступы

**Строки доступа пишутся только на «считывателе доступа»** — том, где уже есть
картотека (обычно `Readers.Num = 1`). На служебных считывателях (`Num = 2`)
строк почти нет: у «Сан пропускника» на входе 234 человека, на выходе — 2.

Алгоритм в `build_add_user_sql()`: для каждого выбранного устройства берём
считыватели, у которых число строк доступа не меньше половины от максимума по
устройству; если картотеки нет вовсе — первый считыватель (`Num = 1`). Слот
считается как `max(InnerNum) + 1` по этим считывателям.

Исключение — устройство «Вход из Зала»: там оба считывателя (25 и 26) рабочие,
и сотрудник получает на них **один и тот же** слот. Так же делает сам Gate.

## Что делает приложение

| Функция (`gate.py`) | Назначение |
|---|---|
| `build_add_user_sql(con, data, user_ptr)` | INSERT в `Users` + `AccessTable`: карта, ФИО, подразделение, доступы со слотами |
| `build_remove_card_sql(card)` | DELETE доступов и пользователя по номеру карты |
| `queue_put(name, sql)` | положить SQL-задание в очередь (cp1251) |
| `queue_restart()` | положить `zz_gateserv_restart.cmd` — перезапуск службы |
| `queue_remove_card(card)` | удалить карту из Gate и перезапустить службу |
| `expire_passes(con)` | истёкшие пропуска: убрать ключ, пометить «истёк» (вызывается из `do_sync` раз в 45 с) |
| `pass_check_job(con, p)` | прочитать результат задания из очереди |

Вызовы: `pass_create()` — запись + перезапуск; `pass_revoke()` и
`pass_delete()` — удаление ключа; `expire_passes()` — по сроку.

**Удаление ключа не делается, если картой пользуется другой действующий
пропуск** — иначе истечение одного пропуска ломало бы второй с той же картой
(эта ошибка была и её исправили).

## Серверная часть на Gate

| Компонент | Где | Что делает |
|---|---|---|
| очередь заданий | `C:\GATE\_skud_queue\` (`\\192.168.2.160\GATE\_skud_queue`) | входные `.sql` и `.cmd`, рядом `<имя>.result`, обработанное уезжает в `done\` |
| агент | `C:\Users\Public\skud_agent.vbs` | выполняет `.sql` построчно и `.cmd` построчно через `cmd.exe` |
| запуск агента | строка в `C:\Users\Public\bridge_watchdog.bat`, задача `GateBridgeWatchdog`, каждые 2 минуты | будит агента |
| перезапуск службы | `C:\Users\Public\PsExec64.exe` | поднимает `C:\GATE\Server\GateServ.exe` в сеансе 1 от `ALM\skudnew` |

Агент открывает базу так же, как Gate: `Microsoft.Jet.OLEDB.4.0`,
`C:\GATE\Server\config.mdb`, workgroup `Gate.mdw`, `User ID=master`.

## Грабли агента очереди

Все три стоили времени — при правке агента их не потерять:

1. **Сторож будит агента только при `*.sql` в очереди.** Условие в
   `bridge_watchdog.bat`: `if exist C:\GATE\_skud_queue\*.sql ...`. Одни `.cmd`
   задания не выполнятся никогда — файлы просто лежат. Обход: класть рядом
   пустой `.sql`.
2. **Запуск `.cmd`-файла напрямую падает с `rc=1`.** Поэтому агент читает файл
   и выполняет **каждую строку отдельным** `cmd.exe /c <строка> >> <результат>`.
   Следствие: переменные (`set`/`%VAR%`), `if`, метки и `goto` в таких файлах
   не работают — только простые команды с абсолютными путями. И ещё:
   `timeout` под перенаправленным вводом не работает, вместо паузы — `ping -n N 127.0.0.1`.
3. **`File.Move` падает, если в `done\` уже есть файл с таким именем.** При этом
   скрипт обрывался и блокировал всю очередь — задания копились и не выполнялись.
   Поэтому в агенте есть `SafeMove`: перед переносом назначение удаляется, а
   каждый файл обрабатывается под `On Error Resume Next`.

Порядок обработки: **сначала все `.sql`, потом все `.cmd`** — сбой на команде
не может помешать записи в базу.

## Как проверить, что всё живо

```sh
# очередь на сервере Gate (SMB)
smbclient '//192.168.2.160/C$' -U 'ALM\skudnew%<пароль>' -m SMB3 \
  -c 'cd GATE\_skud_queue; ls'

# служба приложения на LXC
ssh root@192.168.2.193 'systemctl is-active skud-gate'

# состояние пропусков
curl -s -b cookies 'http://192.168.2.193:8110/api/passes'
```

Признаки проблемы:

| Что видно | Причина |
|---|---|
| задания лежат в очереди, `.result` не появляется | агент не запускается: в очереди нет `*.sql` либо завис на `File.Move` |
| `.result` есть, но в журнале проход без имени | у пользователя в Gate выставлен срок (`UseExpiry = 1`) |
| карта не открывает дверь, в журнале «Неразрешенный ключ» | не было перезапуска GateServ или слот конфликтует |
| карта не открывает, в базе её нет | удалил `expire_passes` (истёк другой пропуск с той же картой) |
