## Авторизация

- Форма входа `/login`, пароль проверяется на сервере.
- Сессия — подписанная HMAC-cookie на 12 часов (`session_hours`).
- Без сессии: HTML → редирект на `/login`, API/выгрузки → `401`.
- Дополнительно принимается HTTP Basic (удобно для скриптов и curl).
- Выход — кнопка «⎋ Выход» (`/logout`).

## Откуда данные

Сервер Gate-IP `192.168.2.160`, SMB-шара `\\192.168.2.160\GATE`:

| Что | Путь | Содержимое |
|---|---|---|
| Суточный журнал | `Server\Events\nГГММДД.mdb` | таблица `Events` — все события дня |
| Конфигурация | `Server\config.mdb` | `Users` (сотрудники), `Groups` (подразделения), `Devices` (двери) |

Проход = `EventType=1` и `EventCode=8` («Проход совершен»); направление
(вход/выход) определяется по названию точки, напр. `КПП1 - Вход`.

**Приход** — первый проход дня, **уход** — последний. Для сегодняшнего дня у тех,
кто ещё внутри, часы считаются до текущего момента и ставится метка «на объекте».
Опоздание и ранний уход считаются от границ смены (по умолчанию 08:00–17:00,
меняются в интерфейсе).

Сервис сам раз в 45 секунд догружает сегодняшний журнал и раз в 10 минут
обновляет список сотрудников.

## API

Все эндпоинты (кроме `/login`) требуют сессию или Basic-авторизацию.

| Запрос | Что отдаёт |
|---|---|
| `GET /api/status` | состояние базы, время последней синхронизации |
| `GET /api/kpi?day=` | проходы, входы/выходы, на объекте, тревоги, по часам |
| `GET /api/stream?day=` | **SSE**: поток проходов вживую |
| `GET /api/live?day=&limit=&all=1` | лента событий (`all=1` — вместе с дверными) |
| `GET /api/presence?day=` | кто на объекте (последний проход — вход) |
| `GET /api/analytics?from=&to=&group=&points=` | данные для всех графиков + сравнение с прошлым периодом |
| `GET /api/late?from=&to=&group=&search=` | опоздания по сотрудникам |
| `GET /api/person?user_ptr=&from=&to=` | карточка сотрудника: дни, часы, опоздания |
| `GET /api/users?group=&search=&user_ptr=` | отчёт о пользователях |
| `GET /api/employees?group=` | справочник сотрудников по алфавиту |
| `GET /api/reports/preview?from=&to=` | счётчики для вкладки «Отчёты» |
| `GET /api/events/summary?from=&to=` | сводка журнала событий СКУД |
| `GET /api/events/list?from=&to=&type=&search=&message=&alarms=1&limit=&offset=` | журнал событий (`search` — ФИО/табельный/текст, `message` — точное событие) |
| `GET /api/points`, `/api/groups` | контрольные точки, подразделения |
| `GET /api/report?from=&to=&view=&group=&points=&search=&user_ptr=&shift_start=&shift_end=` | отчёт |
| `GET /api/sync?days=3` | догрузить журнал |
| `GET /export/1c.csv?...&enc=cp1251&sep=semicolon&dec=,&header=1` | файл для 1С |
| `GET /export/report.xls?...` | оформленный отчёт для Excel |
| `GET /export/users.csv`, `/export/users.xls` | отчёт о пользователях |
| `GET /export/events.csv?from=&to=&message=&alarms=1` | весь журнал событий в CSV |
| `GET /print?view=detail\|summary\|late\|absent\|users\|events&...` | печатный документ (→ PDF из браузера) |

`view`: `detail` (по дням) · `summary` (свод) · `late` (опоздания) · `absent` (не приходили).

`points` — одна или несколько контрольных точек через `|` (например
`points=КПП1 - Вход|КПП2 - Вход`). Пусто или не задано — все точки.
Одиночный параметр `point` тоже принимается.

Пример через curl:

```bash
curl -s -u vitosamin:Admin910327 http://192.168.2.72:8095/api/status
curl -s -u vitosamin:Admin910327 -o otchet.csv \
  "http://192.168.2.72:8095/export/1c.csv?from=2026-11-01&to=2026-11-17&enc=cp1251"
```

## Выгрузка в 1С

Колонки CSV:

```
ТабельныйНомер;ФИО;Подразделение;Должность;Дата;Приход;Уход;Часов;
Проходов;ОпозданиеМин;РаннийУходМин;КонтрольныеТочки
```

Для 1С:Предприятие 8 под Windows — кодировка **Windows-1251**, разделитель
**точка с запятой**, дробная часть — **запятая**, строка заголовков — **да**.
Читается через «Загрузка данных из файла» / «Список значений → Загрузить из файла».

Файлы скачиваются через `fetch` + Blob, поэтому загрузка не блокируется
браузером и внизу справа появляется подтверждение с именем и размером файла.

## Ограничения

- Учётные данные Gate и пароль сервиса лежат в `gate.config.json` открытым
  текстом — файл не публиковать, доступ к сервису только в локальной сети.
- Данные обновляются не мгновенно, а раз в 45 секунд (Gate пишет журнал файлами).
- Опоздание/ранний уход зависят от границ смены: для сменных цехов задавайте
  свои значения в фильтрах отчёта.
- Графики нарисованы собственным SVG-кодом (без Chart.js и CDN) — работает
  в закрытой сети без интернета.

## Печать отчётов

`Печать` открывает готовый документ и сразу вызывает диалог печати:

- шапка: название отчёта, пояснение, период, число записей, дата формирования;
- блок показателей (сотрудников, человеко-дней, часов, минут опозданий…);
- таблица с **повтором шапки на каждой странице** и запретом разрыва строки;
- колонтитул с источником;
- A4: альбомная для «УРВ» и журнала событий, портретная для остальных;
- из диалога печати сохраняется в PDF.

Журнал событий печатается не больше 2000 строк за раз (в шапке видно «Показано»);
полный журнал — через CSV.

## Выбор сотрудника по фамилии

Во вкладках **«Отчёты»**, **«Посещаемость»** и **«Выгрузка в 1С»** есть поле
**«Сотрудник»** — выпадающий список всех работников по алфавиту (287 человек).
Работает как обычный select: начните печатать фамилию — список перескочит
на неё.

Выбранный человек фильтрует **все** отчёты и выгрузки: УРВ, свод, опоздания,
не приходили, отчёт о пользователях, журнал событий, CSV для 1С и печать.
Пустое значение — все сотрудники.

## Несколько контрольных точек

В полях **«Контрольные точки»** (вкладки «Отчёты», «Посещаемость»,
«Выгрузка в 1С», «Аналитика») можно отметить **сколько угодно точек** галочками:

- «все точки (без фильтра)» — снять выбор;
- одна точка — в поле видно её название;
- несколько — «выбрано точек: N».

Фильтр действует на все отчёты: УРВ, свод, опоздания, не приходили,
журнал событий, CSV для 1С, Excel, печать и графики аналитики.

Пример: `КПП1 - Вход` + `КПП2 - Вход` за 17.11 — 164 человека вместо 169
по всем точкам; за неделю 961 запись УРВ.

## Пользователи и права

Вкладка **«Настройки»** видна только администратору.

**Роли:**

| Роль | Что может |
|---|---|
| `admin` — Администратор | всё: отчёты, выгрузки, пропуска (выдача/отзыв/удаление), пользователи, доступ к Gate, пароли |
| `operator` — Оператор | отчёты и выгрузки, **выдача и отзыв пропусков**; удалять пропуска и заходить в «Настройки» не может (403) |
| `viewer` — Просмотр | только просмотр и выгрузка отчётов; выдавать пропуска и менять настройки не может |

**Добавить пользователя:** Настройки → «Пользователи» → логин, имя, пароль
(мин. 6 символов), роль → «Добавить». Там же можно сменить роль в списке,
задать новый пароль кнопкой «Пароль» и удалить пользователя.

Защита: нельзя удалить или разжаловать последнего администратора.

**Хранение:** `users.json` рядом с сервером, пароли — PBKDF2-SHA256
(120 000 итераций, своя соль), файл с правами `0600`, в git не попадает.
Сессия — подписанная cookie на 12 часов, роль проверяется на каждом запросе,
поэтому смена прав действует сразу.

## Смена доступа к серверу Gate

Настройки → **«Доступ к серверу Gate»**: логин и новый пароль учётной записи
SMB (`alm\shapovalenko`), которой сервис читает шару `\\192.168.2.160\GATE`.

- «Проверить связь» — только проверка текущей учётки;
- «Проверить и сохранить» — сначала подключается с новым паролем, и только
  если Gate его принял, записывает в `gate.config.json`. Не принял — старый
  пароль остаётся, в ответе текст ошибки.

Так можно заменить `Adminfzd13m08g07` на любой другой, не трогая файлы на сервере.

**Свой пароль:** Настройки → «Мой пароль» (нужен текущий).

## Пропуска

Вкладка **«Пропуска»** — реестр людей, которым выдан доступ.

**Выдать пропуск:** ФИО (или только номер карты), должность, организация,
документ, телефон, к кому, цель визита, **дата приёма**, **действует до**,
**двери** (мультивыбор), **график** (дни недели + часы) и карта.

- **По номеру карты.** Галочка «выдать по номеру карты» — ФИО можно не заполнять,
  человек подписывается как «Карта AA-BB-CC-11». Нужны только номер, даты и двери.
- **Считыватель карт.** Поле «Карта» принимает номер с USB-ридера, который
  работает как клавиатура (прикладываешь карту → номер появляется, Enter
  подтверждает). Кнопка «⌁» переводит поле в режим ожидания карты.
- **Проверка дублей.** Если карта уже занята действующим пропуском, сервер
  предупредит номером этого пропуска.
- **Статусы:** действует · ещё не действует · истёк · отозван; отдельная метка
  «вне графика», если сейчас время не попадает в расписание.
- **Печать** — карточка пропуска A6: номер, ФИО, должность/организация, даты,
  график, карта, двери, кто выдал и место для подписи.
- **Поиск** — по ФИО, организации, номеру пропуска, номеру карты и документу.

Выдавать и отзывать могут `admin` и `operator`; удалять — только `admin`.

## Готовность ключа в Gate

Пропуск в нашем реестре **сам по себе не открывает двери** — карту должна знать
СКУД Gate. Поэтому в списке есть колонка **«Готовность в Gate»**, которая
считается по реальной картотеке Gate:

- читается `Users` (карты: `Number`, `NumberU`, `NumberMifare`),
- `AccessTable` (какие считыватели разрешены пользователю),
- `Readers` (считыватель → дверь).

Для каждого пропуска видно:

| Показатель | Что значит |
|---|---|
| зелёная полоса `3/3` | карта есть в Gate и открывает все выбранные двери |
| жёлтая `1/3` | карта есть, но не на все двери |
| красная «нет в Gate» | номера нет в картотеке — ключ не выдан |

Клик по ячейке открывает карточку: найденный в Gate сотрудник, табельный и
построчный список дверей с отметками «ключ добавлен / нет доступа».

Кнопка **«Обновить из Gate»** перечитывает картотеку (`/api/sync?days=0`),
иначе она обновляется раз в 10 минут и при старте сервиса.

Номер карты сопоставляется в разных записях: `104/18643`, `18643`, `0000006848D3`
(hex из `NumberU`), с ведущими нулями и без.

## Ключи заводятся из приложения (без GateTerm)

> Подробное описание механизма, найденных граблей и порядка проверки — в
> отдельном документе [`KEYS.md`](KEYS.md).

Приложение само создаёт ключ в СКУД Gate. Схема:

```
Пропуска → «Выдать пропуск» (карта + двери)
        → приложение пишет SQL-задание и задание на перезапуск в очередь
        → агент на Gate (каждые 2 минуты) выполняет SQL в config.mdb
        → и сразу перезапускает GateServ — только тогда ключ уходит в контроллеры
        → карта открывает двери, проход в журнале с именем
```

**Главное (выяснено 18.11):** запись в `config.mdb` сама по себе дверь не
открывает. Контроллер узнаёт ключ только после **перезапуска GateServ** — служба
читает картотеку при старте. Поэтому после каждого пропуска в очередь кладётся
ещё и `zz_gateserv_restart.cmd`; имя постоянное, несколько пропусков подряд
дают один перезапуск.

**Обратная сторона: отозвать ключ так нельзя.** Служба пишет ключи только в
**свободные** слоты, а занятый слот не перезаписывает и не очищает. Поэтому
удаление записи, блокировка (`Status = 1`), подмена карты и команда Gate
«Передача ключей в контроллеры» ключ из контроллера **не убирают** — карта
продолжает пускать. Проверять это можно только картой у двери, не по базе.
Что уже пробовали и какой шаг следующий — в [`KEYS.md`](KEYS.md).

**Слот ключа — один на устройство.** Память ключей у контроллера общая для всех
его считывателей, поэтому `AccessTable.InnerNum` должен совпадать у считывателей
одного устройства и быть свободным на устройстве. Если выделять слот каждому
считывателю отдельно (как было сначала), ключ попадает в занятый слот, и
контроллер отвечает «Нет доступа. Неразрешенный ключ».

**Строки доступа — только на «считывателе доступа»** (том, где уже есть
картотека, обычно `Readers.Num = 1`). На служебных считывателях строк нет.

**Срок действия в Gate не выставляем** (`UseExpiry = 0`): у всех 288 сотрудников
он пуст, а пользователя с заполненным сроком Gate не сопоставляет с событием —
проход в журнале остаётся без имени. Срок пропуска ведёт наше приложение, а ключ
убирается при отзыве, удалении и по истечении (`gate.queue_remove_card`, фоновая
проверка `gate.expire_passes` раз в 45 с). Если картой пользуется другой
действующий пропуск, ключ не удаляется.

**Что нужно на сервере Gate (уже настроено):**

| Компонент | Где |
|---|---|
| очередь заданий | `C:\GATE\_skud_queue\` (`\\192.168.2.160\GATE\_skud_queue`) |
| агент | `C:\Users\Public\skud_agent.vbs` (32-битный `cscript`) |
| запуск | строка в `C:\Users\Public\bridge_watchdog.bat`, задача `GateBridgeWatchdog`, каждые 2 минуты |

Агент открывает базу так же, как Gate:
`Microsoft.Jet.OLEDB.4.0`, `C:\GATE\Server\config.mdb`, workgroup `Gate.mdw`,
`User ID=master`.

**Грабли агента** (все три стоили времени):
- сторож запускает агента, только если в очереди есть `*.sql` — одни `.cmd`
  задания не разбудят;
- запуск `.cmd`-файла напрямую падает с `rc=1`, поэтому агент выполняет файл
  **построчно** через `cmd.exe /c <строка>` (переменные и `if` в таких файлах
  не работают — только простые команды);
- если в `done\` уже лежит файл с таким именем, `File.Move` падает и скрипт
  обрывается, блокируя всю очередь — перед переносом назначение удаляется
  (`SafeMove`).

**Как это устроено в коде:** `gate.build_add_user_sql()` собирает INSERT в
`Users` и `AccessTable`, `gate.queue_put()` кладёт задание,
`gate.queue_restart()` — перезапуск службы, `gate.pass_check_job()` читает
результат.

**Важно:** номер карты должен быть в формате Gate — `140/39939`
(`facility/card`). Если карта в другом виде, задание не создаётся, пропуск
остаётся только в реестре.
